## C. Findings from the first live P3 run (2026-11-25) and what changed

The first run of `tests/test_live_p3.py` passed all 7 tests, but reading the artifacts showed problems the tests did not catch. The tests were then **tightened**, not relaxed; the code was fixed.

| Finding | Evidence | Change |
|---|---|---|
| Demo B: 3 of 4 must-answer topics were wrongly UNSUPPORTED (stock at ports, best price, arrival time). | `runs/p3_checkpoint/` first run: probes invented parts that are not in the catalogue ("500 kW diesel generator control panel"), and verified table-row spans were rejected as "too short" (`stock_port: Singapore`). | Probes are now grounded in real corpus excerpts (`guard/probes.md` v2); probes with no content term of the topic are dropped; table-row chunks need only 2 tokens instead of 3. |
| Calibration reported LOW CONFIDENCE on every corpus, and the spec's fallback (midpoint of medians, 0.70 to 0.74) would gate out relevant chunks. | In-scope p10 0.675 vs near-miss p90 0.808 on Demo A. Near-miss probes on the same subject embed as close as answerable ones. | When distributions overlap, `min_score` = in-scope p10 minus 0.05 (recall-preserving); unanswerable near-misses are left to the refusal policy. | Intake question text sometimes repeated the whole brief. | `00_intake/questions.json` for Demo B. | `intake/question.md` v2: do not quote the brief, at most 30 words. |

Known limitation (kept, to appear in the final report): the guard's extractive check proves a span exists and shares a content term with the topic or on-topic probe; it does not prove the span *answers* the probe. A topic whose only matching text is tangential could be marked SUPPORTED.

Process notes: Demo corpora are synthesised by `data/synthesis/synthesize.py`. Generated clauses are filtered in code: clauses with numbers or spelled-out quantities that are not in the plan, forbidden words, or list markers are dropped, so the corpus has no accidental contradictions with the planted facts (the first Demo A draft said "two weeks" notice where the plan says 10 working days). Demo B supplier-terms PDFs are 3 pages each (the spec's 4 to 6 pages applies to Demo A).

**Second finding, same day (a regression I introduced and the live tests caught).** After grounding the probes and letting the relevance check also use the probe's terms, Demo A's payroll gap *disappeared*: for the topic "Salary slip interpretation" the model saw leave-policy excerpts, asked leave questions that merely mentioned the topic, and the real leave spans were accepted as support (`test_demo_a_flags_the_payroll_gap` failed, correctly). Fix: relevance uses the **topic's** terms only (the probe's terms are never evidence, because a drifting probe always shares terms with the text it retrieved); table rows count as a whole record; content-term stems are 6 letters instead of 5 ("interpretation" no longer matches "internal"). A unit test reproduces the drift (`test_drifting_probe_cannot_launder_unrelated_text_into_support`). SPEC 4.1's relevance rule stands as written above (verbatim span plus topic-term overlap).

**Third finding (same day).** Even with the guard fixed, Demo A produced no gaps: the draft model labelled its must-answer topics `resolved_from_docs`, and `verify_confidence` checked them only against the documents, so "Salary slip interpretation" (asked for by the brief, absent from the documents) was dropped *before the guard ever saw it*. The verification now accepts support from either the brief or the documents, and everything it drops is recorded in `00_intake/draft_verification.json` together with the raw model draft. Regression test: `test_a_requirement_from_the_brief_is_kept_even_if_the_model_credits_the_documents`. Lesson recorded: a check that silently removes requirements is itself a way to lie; its removals must be visible.

**Residual limitation after the fixes (Demo B).** The guard marks the topic "What spares are in stock at each port?" UNSUPPORTED: the model's probes for it are vague ("as provided by suppliers S02 and S03") and the extractor finds no span. The catalogue does have a static `stock_port` snapshot, so a better outcome would be "answerable from the snapshot, with a not-live disclaimer". It lands on the intended behaviour for this demo (the agent must not claim live stock) for a partly wrong reason. Reported, not hidden; the structural live-data gap `G-LIVE-1` is flagged independently of it.

**Calibration result (all runs).** Every corpus reports `separable: false` with `min_score` about 0.66, meaning dense similarity alone cannot tell same-subject unanswerable questions from answerable ones with bge-small. The recall-preserving rule is in force; whether it helps or hurts end-to-end accuracy will be measured by the evals in P5 to P7 rather than assumed.

**Fourth finding (same day): interview answers inverted a rule.** Reading `requirements.md` for Demo B showed `scope.out` items such as "The assistant should not avoid topics related to compliance". The question had been phrased as yes/no, the model's answer was "no", and the list-splitting step turned the sentence into items. Compiled into an agent prompt that would have flipped a rule. Fixes: question prompt v3 asks open questions only; `apply_answer` v2 requires short noun-phrase topics and an empty list for "none"; `clean_items` drops sentence-like items in code (regression test added). Remaining known risk, for the report: in `--non-interactive` mode the self-answered `scope.out` and `must_refuse` lists can still contradict the corpus (Demo A's self-answer excludes "misconduct reporting", which the Code of Conduct covers). They are labelled ASSUMPTION; a human checkpoint (stretch goal 1) is the real remedy.


## D. P3 corrections requested after the first P3 review (2026-11-25)

**1. Assumption precedence: brief > corpus evidence > assumptions.** In `--non-interactive` mode a self-answered exclusion (`scope.out`, `must_refuse`) is probed like a topic. If it overlaps a topic the brief asks for, or the corpus can answer questions about it, it is dropped and recorded under `assumptions_rejected` (with the evidence spans). Exclusions about things the corpus does not cover are what assumptions may add. Items from the brief or from a human answer are never touched. Regression tests: `tests/test_precedence_and_split.py` (offline) and `test_live_p3.py::test_demo_a_keeps_misconduct_reporting_in_scope` (live). On Demo A the first run after the change rejected `misconduct reporting` (and 7 other items) as corpus conflicts.

**2. Split partially supported topics instead of refusing them whole.** After the first probe round, every not-fully-supported topic, and every topic tied to a live-data gap even if supported, is split by the model into at most 3 aspects. Aspects are probed with the same two checks and anchored to the PARENT topic's terms, so an aspect that drifted cannot be supported by unrelated text. Supported aspects stay as `supported_aspects`; unsupported ones become gaps; a topic with no supported aspect stays a whole gap. Nothing is specific to stock or shelves. Supporting decisions:
- A live-data gap is tied to the ONE closest must-answer topic (embedding similarity, with at least one shared content term). Word overlap alone tied too many topics, and the gap evidence is now the clause containing the live cue, not the whole sentence (a second request in the same sentence, the cafe, had been tied to the live gap).
- The model's `needs_live_values` label is honoured only for live-tied topics. On other topics it is ignored, so a loose label cannot turn a missing document into "live data" (it labelled "renewal availability" as live).
- A static snapshot supports the recorded part of a live topic; the answer carries `snapshot_as_of`, read from the evidence rows (a `snapshot_date` column or an "as of <date>" phrase), and the generated agent says "as of <date>" and never calls it current.
- **Spec deviation:** the Demo B catalogue gained a `snapshot_date` column (SPEC 11 lists nine columns). The non-demo library fixture gained `books.csv` (title, author, shelf, copies, snapshot_date) so that "which shelf is this book on" (supported) versus "is it on the shelf right now" (live gap) can be shown on a non-demo corpus.

**3. Second support check by the judge model.** A probe is supported only if (1) the code check passes (verbatim substring, long enough, topic term) AND (2) the judge model, from a different family, says the span answers the question and quotes the words that hold the fact; that quote is verified as a substring of the span. A topic needs both on at least 2 of 3 probes. `coverage.json` reports `check_agreement` (both pass / code only / judge only / neither / disagreement rate). The judge sees the span and the whole record it came from (a table fragment like `stock_port: Singapore` means nothing without its row). Judge calls are batched after all agent-model calls to limit model swaps.

Judge prompt iterations, each found by reading artifacts (all measured on Demo A, Demo B and the library fixture):

| Version | What happened |
|---|---|
| v1 (span only, yes/no first) | gemma3:4b was lenient: it said yes to leave spans for salary-slip questions (judge-only passes 8 to 10 per run). llama3.1:8b was strict: it rejected 17 of 29 valid table-row spans. |
| v3 (record added, "facts needed" wording) | llama still said no to "maximum fine for an overdue DVD" with the span "capped at 15 dollars per item". |
| v4 (reason, then quote, then verdict) | Reasoning-first schema fixed it. Topic verdicts match expectation on all three corpora for llama3.1:8b (12/12 topics); gemma3:4b gets 11/12 (Demo B stock topic PARTIAL). |

**Judge model choice (provisional, to be confirmed or overturned by the P6 canary comparison).** The configured judge is now `llama3.1:8b`. Evidence so far: the P4 tool-necessity review scores 8/8 with llama3.1:8b and 6/8 with gemma3:4b (gemma wrongly rejects needed tools), and the guard role is equal or better. The code check remains the authority: the judge can only veto a code-verified span, never create support, and the two checks' disagreement is reported.

**4. Future option, not built:** a cross-encoder reranker (for example `bge-reranker-base`) as a P7 retrieval patch. Bi-encoder scores were not separable (every corpus calibrates as `separable: false`), and a reranker scores query and chunk jointly, so it may separate same-subject unanswerable questions from answerable ones where cosine similarity cannot.

**Calibration change.** The in-scope side of the `min_score` calibration now uses the similarity of the chunk that HELD the verified span (`evidence_dense`), not the best similarity to any chunk. The first calibrated agent (library) set `min_score` 0.7265 from best-chunk similarities and then dropped the chunk holding the fine rule for a two-part question ("the fine is not specified"). The near-miss side still uses the maximum, because that is what could wrongly pass the gate. SPEC 4.4 updated.

## E. P4: agent generator and tool selector (2026-11-25)

**Deviations from SPEC 5.1 / 5.3, with reasons.**
- Prompt sections are rendered from versioned templates and requirement data. The model writes only `identity` and `audience_tone`, and even those must contain the agent name and an audience term or the template is used. Every section that carries a RULE (refusal policy, grounding, citations, scope) is deterministic, so the refusal policy provably lists every must-refuse topic and every non-warning gap with its redirect (`test_refusal_policy_contains_every_must_refuse_topic_and_every_guard_gap_with_its_redirect`). The spec says the generator LLM fills each section; this is stricter on purpose, and the optimizer (P7) still rewrites single sections with the model.
- `few_shot` is empty in `agent.v0.yaml`. A format example needs a real chunk id and quote, and an invented one would teach citation errors. The optimizer can add one later.
- Tool selection is a three-gate process: (a) the agent model gives one decision per registry tool with a cited must-answer topic; (b) a validator drops unknown, uncited, duplicate or precondition-failing proposals (a table lookup needs a table); (c) the judge model reviews necessity with a rubric ("Needed when / Not needed when" per tool in `prompts/tools/need/`), must first say whether the answer is simply stated in a document, and must quote the words of the topic that show the need (verified in code).
- **Keyword-trap finding.** With only gates (a) to (c), the suite scored 6/8: both model families attached `weather` for "what the supplier terms say about weather-related delivery delays" and `current_date` for "deadlines for submitting travel claims". Same-direction errors from two models cannot be fixed by a second model. A deterministic VETO was added for the two world-state tools: the topic text itself must ask for a time-dependent value (a forecast; today, days until, arrival). A cue never attaches a tool; it can only block one the models agreed on. Suite: 8/8.
- Retrieval parameters come from rules over the document profile (`generator/retrieval_rules.py`), each with its rationale recorded in `agent.yaml`'s provenance; `min_score` and its allowed bounds come from the guard calibration.

**Runner defects found by the smoke questions (not by the unit tests).**
- On Demo B the agent called the same `csv_lookup` three times and never answered (`no_final_answer`). A repeated identical call is no longer executed; once calls are repeated or used up, the model is restricted to a final-answer schema.
- An empty `answer` on a refusal broke the contract; `output_contract` v2 says a refusal must still say something and give the redirect.
- Citation ids written as `c91` instead of `spares_catalogue.csv#c91` are still reported as contract issues after the one repair retry. That is the 8B model's formatting weakness; it is counted, not hidden, and is an optimizer target.

**TODO(P5): few-shot leakage check.** `forgeai/generator/fewshot.py` implements the embedding-similarity check (threshold 0.80) and `validate_few_shots`. It can only run fully once the eval set exists. `agent.v0.yaml` records `fewshot_leakage_check: pending`. In P5 the build pipeline must call `validate_few_shots(agent, eval_questions, embedder, threshold)` before any few-shot example is accepted.

## F. P5 blocker fixes and review follow-ups (2026-11-26)

**1. Contradictory refusals (blocker).** Demo B had "pricing details" and "financial details" as must-refuse topics while the brief asks for cost estimates with discounts. Eval cases are built from the requirements, so this would have produced evals that expect both an answer and a refusal. Fixed in code, generically (`forgeai/intake/consistency.py`):
- Every self-answered exclusion is checked against (a) the topics and asks of the brief, by word overlap and then by embedding similarity plus a judge-model yes/no whose supporting quote must be a verbatim part of the ask; (b) **table schemas**: column names and cell values count as corpus evidence, which is what rejects "pricing" (column `unit_price_usd`); (c) the existing corpus probes. Rejections are logged under `assumptions_rejected` with the evidence.
- Stemmer improved so that price, prices and pricing meet (a column named `unit_price_usd` is evidence for "pricing"; it was invisible with the old stemmer, as the reviewer suspected).
- Invariant: no must-refuse item is contained in a must-answer topic's terms. It runs at the end of every intake (`assert_consistent`) and in `tests/test_consistency.py` over every committed `requirements.yaml`.
- Cost of the fix, kept visible: the judge over-rejects. On Demo A all five self-answered refusals (personal data, legal advice, confidential information, ...) were rejected as conflicting with the broad brief clause "answers HR policy questions", so Demo A now has no must-refuse topics of its own; its refusal evals come from the gaps, near-misses and negative tool cases. The first prompt version rejected more; v2 adds neutral worked examples. A human checkpoint is still the real remedy for unattended precision.

**2. ## G. P5: eval generator (2026-11-26)

**Deviations from SPEC 6.1 / 5.3, with reasons.**
- **Negative tool cases come from the requirements, not from the agent.** SPEC 5.3 asks for a negative case per UNATTACHED tool, but that list lives in the agent's tool selection and the eval generator must never see the agent. The generator uses the tools whose capability the requirements do NOT call for (`capabilities_needed`). If the selector attached a tool the requirements did not name, that tool simply has no negative case.
- **Near-miss and refusal validation.** A near-miss, gap or negative-tool refusal case must make the guard's two-check probe FAIL (`the corpus can answer it` otherwise rejects it). The "max retrieval score below a threshold" condition in SPEC 6.1 is logged (`max_dense_similarity`) but not gated: every corpus calibrates as non-separable (section D), so a similarity gate would reject nearly every genuine near-miss.
- **Paraphrase check uses word trigrams.** Bigrams flagged questions that only reused the passage's vocabulary ("warranty period", "new parts") as copies. A copied question shares nearly all its trigrams. Threshold unchanged (below 0.5).
- **Key facts are atomic and few.** At most 2, at most 10 words, no leading "and/or/but", and a bare quantity is `number` while "31 January" is a `phrase`. The first full run let the model write whole sentences (one case had 20 "key facts"), which cannot be matched reliably. Key facts are asked for as plain strings: with `{text, kind}` objects the constrained decoder emitted empty `text` in 23 of 28 first-run answerable candidates.
- **Independent answerability** (judge answers from the seed alone): the PRIMARY key fact must be recovered plus at least half of all facts, and for multi-document cases each document must contribute a recovered fact. All-facts-recovered rejected questions whose second fact was a detail the question never asked for. The multi-document rule was added after reading a sample: "requirements for personal email accounts" had been labelled multi-document but only needed one policy.
- **Adaptive over-generation.** Round 0 writes about 2x the target per type; up to five top-up rounds write only for types still short, stopping at 28 validated cases. Nothing is padded: the shortfall per type is reported, and surplus answerable, multi-document and out-of-scope cases (never ambiguous or tool cases) top up the total toward 32.
- **Table rows.** The seed span of a row is the whole row; the model's quote must be inside it, and a question about a row must name the values that identify it (otherwise "minimum order quantity for the servo valve" has several answers).
- **Page footers are excluded as seeds** (a "Page 1" line made a trivial multi-document case).
- **Output cap.** `max_output_tokens: 1536` per reply (`num_predict`). One degenerate generation ("1_6_1_7_1_6...") ran into the 600 s timeout and killed a build; generation temperature is 0.4.

**Computed cases (SPEC 6.1 "tool-required").** `forgeai/evals/compute.py`. The model proposes a plan (question, variables bound to a table cell, a number in a quoted passage or a number in the question, a formula, conditions); code verifies every binding against the documents (exactly one row, verbatim span, the number is a real number token and not digits inside an identifier), checks the conditions, requires every variable to be used and, when a table and prose rules are both available, one fact from each, then computes the answer with the safe calculator. Tested deterministically: 12 units at 420.00 under a 5% tier (conditions: order value inside the tier) gives 4788. **Live yield on Demo B was 0 of 12 plans**: the 8B model usually binds a variable it never uses (lead time, MOQ) or writes fewer than two document facts. The tool-required slots are therefore filled by lookup cases (expected value is a table cell). This is reported, not hidden.

**Prose passages for a table row are chosen by shared values, not by retrieval.** Searching the index with a row as the query returned 60 table rows and zero prose chunks. This is the "source diversity in top-k" problem recorded for P7, now observed directly.

## I. P6: the judge (2026-11-28)

**Design (SPEC 6.2-6.4).** `forgeai/judge/`. Layer 1 (`layer1.py`) is code only: contract, status, citation validity (the runner's substring check), source correctness by seed-span overlap of the CITED chunk (multi-document: every expected document), key facts (numbers/currency by value with commas and spelled-out numbers; dates in any format; phrases by substring then rapidfuzz token-set >= 85, with two guards added by me: a phrase that carries a number fails if the number is absent, and a negation in the fact must be in the answer), tool correctness (expected tool called without error, computed value within abs 0.01 / rel 0.1%, only when tools are expected), retrieval hit@k and first-hit rank by overlap. A snapshot case needs the `snapshot_date` key fact in the answer. `relative_date` facts are resolved with `templates.resolve_relative_fact` against the scoring date. Layer 2 (`layer2.py`) runs only on answered cases (and on refusals that carry figures or exceed 40 words): the answer is decomposed into claims, each claim is rated against the retrieved chunks plus the agent's tool results, and "supported" counts only with a quote copied from that context and verified as a substring. A key fact that fails layer 1 can be upgraded only for `phrase` facts, only with a quote that is a verbatim span of the answer, carries the fact's numbers and agrees on negation. Judge prompts receive question/answer/claim/fact/context only; a test renders them and checks for model names, iteration numbers and case ids.

**Deviation: claim support does not show the judge the question** (prompt v2). With the question shown, the first llama run rejected correct claims as "not what the question asks about" (gold control accuracy 0.47). v2 asks only "does the context say this" and the control rose to 0.73.

**Canaries** (`canaries.py`, `forgeai canaries`): 15 gold answers (5 per demo, dev cases with a number in their span), built in code from seed-span text (table rows cut to the key-fact cells plus the row's first cell), cited with verbatim chunk quotes, then perturbed in code six ways (number swap to a number absent from the context, negation, wrong-document citation, fabricated sentence, padded-but-correct with two true chunk sentences, concise-correct) = 102 canaries per judge. Accuracy is reported for the whole pipeline and for layer 2 alone (layer 1 is identical for every judge, and a wrong-document citation is a layer-1 check, so layer 2 is not scored on it).

**Noise floor** (`forgeai noise`): agent v0 re-run on the dev split with a fresh, empty cache for the agent AND the judge, flips counted against the baseline. A hr_shore 1 of 24 (hr-A04), B spares 0 of 20, library_gap 0 of 19. **The floor comes from a single rerun**, so it is a lower-bound estimate of the real variation: a floor of 0 means "no flips seen once", not "deterministic". That is why the confirmation rerun below exists.

**Acceptance gate** (`optimizer/gate.py`): net gain (fixed - regressed) must exceed the noise floor AND regressions <= 1. **Confirmation rerun:** when the gate accepts, only the fixed and regressed cases are re-run once more, uncached. A fix counts only if the case passes on both runs; regressions stay as the first run found them (a regression that passes on the rerun is not forgiven). If the confirmed gain no longer clears the gate the patch is reverted and logged `rejected: unconfirmed`. A fix that did not hold is also written back into the dev result, so dev scores never count a pass that held once. `change.json` carries `status` and a `confirmation` block.

**Classifier** (`optimizer/classify.py`): spec 6.5 exactly; every failure gets one of retrieval_miss, prompt_defect, hallucination, wrong_refusal plus a section for prompt defects. A failure decided by a layer-2 verdict of a type under 90% on the canaries (currently `padded_correct`) is `low_confidence`; the loop counts the others first. **Patch library** (`optimizer/patches.py`): the spec table with bounds (top_k <= 10, chunk size 120..800, overlap <= 40%, bm25 weight <= 0.8, min_score only inside its own bounds, temperature only down), plus source diversity (`retrieval.reserve_prose`: slots of top-k kept for prose chunks, at most half of top_k). **Not implemented:** the format-only few-shot patch and the explicit gap-refusal patch of the spec table; the cross-encoder reranker (section D) is NOT built because it is only worth it if retrieval misses still dominate after the patches.

**Anti-overfitting guard** (`optimizer/guard.py`): a drafted prompt text is rejected if it contains a dev question, an expected value or a case id; every rejection is logged in `rejected_patches.json`. The optimizer never sees the test split: test scores are computed by `iterate.py` into `sealed/` through the `after_iteration` hook.

**Results** are in `runs/p7_checkpoint/*/04_iterations/` and the P7 report; they are small and mixed, see the report. One accepted patch (spares: top_k 6 to 8, bm25 weight 0.5 to 0.7) raised dev 12 to 15 (3 of 3 fixes confirmed) and lowered the sealed test split 5/8 to 4/8: the lost case (sp-A06) fails on an invalid citation (`chunk_id 'c5'` does not exist), a model formatting slip with a larger context. Dev gain did not generalise on 8 test cases; the test split is not used to choose patches.
